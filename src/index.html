Installing Catalyst Link

Catalyst Link runs on the laptop beside the robot project's git repo. It serves the tablet read-only code, turns the tablet's proposed edits into a branch in their own worktree (never merged, never deployed), keeps an inbox of work orders for the PC's own coding agent, receives recordings and logs off the tablet's microSD, and forwards Claude through this PC so no API key ever lives on the tablet. It lives in the Bezel repository, under tab5/link.

THE SERVICE

Python 3.10 or newer, and git.

cd tab5/link
python -m pip install .            # the catalyst-link command
python -m pip install zeroconf     # optional: lets the tablet find it by mDNS
python -m pip install ".[media]"   # optional, Windows: the media remote
python -m pip install ".[flash]"   # optional: esptool, for the firmware panel

Then point it at your robot project and start it. It prints its address and its token, and state lives in ~/.catalyst-link/.

catalyst-link serve --repo ~/robot --check "./gradlew compileJava"
THE WINDOW AND TRAY ICON

The same Link with a window around it — status, pairing, the firmware panel, the recordings, the inbox, the log. Built the way this app is: Tauri 2, plain HTML/CSS/JS, no bundler. Needs Node.js and Rust with the MSVC toolchain to build.

cd tab5/link/desktop
npm install
npm run build

The installer lands in src-tauri/target/release/bundle/nsis/. On first start it asks for the robot project, and the Link starts as soon as one is set. If a Link is already answering on the port it attaches to that one instead of starting a second.

Pairing is how the tablet gets in. On the tablet, settings → home → pair the pc; it lists the Links it finds by mDNS, you tap this PC, and the Link shows a six-digit code to type on the tablet. Each paired tablet gets its own token, so one can be forgotten without re-pairing the others.

Flashing the tablet

Not from here. Firmware lives in tab5/firmware/, and Catalyst Link's desktop app has a firmware panel that writes it with a button — it lists the serial ports and marks the one whose USB vendor id is Espressif's, shows esptool's own output as it goes, and counts a flash as done only once esptool says it verified what it wrote. That needs esptool in the Python that runs the Link (python -m pip install ".[flash]").

Use the USB-C port. That port is the ESP32-P4's USB-Serial/JTAG. The USB-A port is the robot tether — it is a host port for the Systemcore or a USB-Ethernet adapter, and it cannot flash the tablet. Plugging into the wrong one looks like a tablet that will not connect.

Two images, and the difference matters. The merged image covers the settings area, so writing it erases the tablet's pairing, Wi-Fi and settings; the app alone leaves them. Choose "the app only" for an update.

esptool.py --chip esp32p4 -b 921600 write_flash 0x0 catalyst-tab-merged.bin   # everything, erases settings
esptool.py --chip esp32p4 -b 921600 write_flash 0x10000 catalyst_tab.bin      # the app alone

The addresses, the other images and what to do when it will not start are in tab5/firmware/README.md.

What the tablet shows

One screen per job, paged rather than nested, so a number can be found without navigating to it. It is a pit and bellypan instrument first: everything below works while you are standing at the robot rather than sitting behind the driver station.

Pulse — the one-glance overview: mode and alliance, battery and brownout risk, loop time against its budget, and how many errors and warnings the robot is reporting.
Devices — the motors, cameras and controller the robot expects against the ones that actually answered, and what each Limelight thinks of itself.
Power — the power module's channels and what each one feeds, with live current where the team publishes it.
Motion and field — where the robot thinks it is, each swerve module's target against what it is doing, and the path it is following.
CAN — utilisation and health per bus, the device roster, and a CAN tap that works with the robot code dead, which is the one thing no laptop on the cart can do.
Alerts and health — every error, warning and per-subsystem health item the robot raises, with the subsystem that raised it.
Preflight — the pre-match checks and the results of the diagnostic routines, and which Driver Station op mode to run for the ones it cannot run itself.
Tune and auto — the tunables the robot declares and the autonomous choice. These are the only two things the tablet writes.
Controls and states — the driver bindings the robot reports, and the whole-robot state machine as it moves.
Motors — each motor by serial number: lifetime hours, revolutions, peak current and temperature, and every id and name it has ever carried.
Recorder and logs — an on-device black box that records a run and plays it back, and a reader for the Driver Station logs off a microSD card.
It never controls the robot. The tablet inherits Catalyst Console's rule: the only writes it makes are a tunable the robot declared, the autonomous choice, and a Limelight's LED to identify which camera you are looking at. Every diagnostic routine is a Driver Station op mode — the tablet shows the result and says which one to run. And a value the robot is not publishing reads as —, never as zero.

Import a project

Any WPILib project, already written, whether or not Catalyst is in it. Pick the folder with build.gradle in it and Catalyst reads it and reports what it found — season, installed Catalyst version, where that library resolves from, and the rest of vendordeps. It writes nothing and changes nothing. To add Catalyst to a project, use the Library page instead.

What an agent can do

Nothing outside a registered folder is reachable at all. The workspace's Claude session is bound by the same rules.
